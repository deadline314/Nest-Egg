# [NE-170] 加快測試：平行、只測受影響範圍、完整測試交給 CI

> 狀態：完成

## 內文

### 需求
完整測試要循序跑十幾分鐘，每張票交付前都跑一遍太慢。要讓測試更快：能平行跑；平常只測有更動到的範圍；完整測試放到 CI，每次推送、每個 PR、每小時一次（程式有更動才跑）。

### 來源
2026-10-04，使用者要求更快的測試方法、不要每次都做完整測試只測更動的範圍，並把完整測試放到 CI 排程（每一小時加上程式有更動時執行）。

### 驗收條件
- [x] 完整測試可以平行跑：把測試分成幾組同時執行，各組的存檔互不覆蓋，結果合併顯示總檢查數與失敗項目
- [x] 平行完整測試的總時間明顯短於循序跑（同一台機器比較）
- [x] 能依 git 的更動（提交、未提交的修改、新檔案）挑出受影響的測試只跑那些；只改文件或票時不跑任何測試；改到整個專案設定或測試流程本身時跑全部
- [x] 改單一工具或資料只挑到少數相關測試，改到被大量使用的核心才挑到很多
- [x] 已知失敗有一份清單；平行測試與 CI 只有出現新的失敗才不通過，已知失敗在輸出裡標示
- [x] CI 在每次推送到 main、每個 PR、每小時一次執行完整測試；每小時那次如果這個提交已經有成功的測試就略過；失敗時保存各組的完整輸出
- [x] 開發守則改成：交付前跑受影響範圍的測試，完整測試由 CI 負責

### 測試流程
1. 改一個工具檔，執行受影響範圍的測試，確認只跑相關的幾個套件
2. 只改一張票的文字，確認沒有測試要跑
3. 執行完整平行測試，確認結果與循序跑一致（已知失敗之外沒有新增失敗）
4. 推送後在 CI 看到測試執行並通過

# Commit-1

## 內文

完整測試循序跑要十幾分鐘，每張票交付前都跑一遍太慢，而且很多票只動到一小塊。
現在有三種跑法：
- **平行完整測試**：把測試分成幾組（預設核心數加二），每組用獨立的程序同時跑，各組的存檔資料夾分開，不會互相覆蓋；耗時記下來，下次依耗時平均分組。同一台四核機器上，完整測試從循序的十幾分鐘縮短到約 2 分 50 秒（27111 項檢查）。
- **只跑受影響的範圍**：依 git 的更動（相對 main 的提交、未提交的修改、新檔案）做影響分析，挑出會用到這些檔案的測試套件再平行跑。改單一工具或資料只挑到少數相關的套件，改到被大量使用的核心（玩家、音效庫…）才挑到很多；只改文件或票時不跑任何測試；改到專案設定或測試流程本身就跑全部。
- **CI 完整測試**：每次推送到 main、每個 PR、每小時一次（排程那次若這個提交已經有成功的測試就略過）自動跑完整測試，失敗時保存各組完整輸出。
已知失敗（main 上就有的 10 項，包含兩項時序不穩定的檢查）列在一份清單裡，平行測試與 CI 只有出現新的失敗才不通過。開發守則改成：交付前跑受影響範圍的測試，完整測試由 CI 負責。
過程中順手修了平行跑才暴露的兩個問題：離開關卡後診斷面板會讀到已經釋放的鏡頭計數器而報腳本錯誤（鏡頭離開時取消登記，讀取時也跳過已釋放的主人）；「最舊的屍體淡出」檢查改成等到條件成立而不是固定等幾格，機器忙時不再誤報。
驗收：完整平行測試與循序結果一致（新失敗 0）；影響分析抽查——改實驗室編輯器只挑到實驗室相關 3 個套件、改近戰資料挑到 10 個、改玩家挑到 37 個、只改票文字挑到 0 個。推送到 main 後 GitHub 上的 CI 實際執行並通過：下載引擎、匯入專案約 7 分鐘（之後有快取）、完整測試 5 分 15 秒。
