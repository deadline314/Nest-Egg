# [NE-431] 清掉測試與工具債並修第四章冷啟動

> 狀態：進行中

## 內文

### 需求
前一個玩法 session 與這幾天的多線作業留下一批測試與工具上的問題，其中一項可能是玩家會遇到的存檔問題。每一項都要有結論（修好、或查明不是問題並說明理由）：

1. 第四章的流程探針在「原帳」那一步失敗：從 Atropos 競技場的存檔冷啟動繼續時沒有回到安全臺。查出從什麼時候開始壞、根因是什麼，確認玩家實際會不會遇到（在競技場存檔、關掉遊戲、重開繼續，人出現在哪裡）；會遇到就修並補回歸。
2. 列出不在測試挑選規則與 CI 裡的流程探針，該進的放進去。
3. 測試挑選工具挑得準：改共用的敵人、玩家、關卡基礎程式不能漏挑（例如改 grunt.gd 只挑出 10 個、實際要 43 個），改一個道具或一個資料欄位也不能展開成幾乎全部。
4. 跑測試的腳本與探針不把整份輸出接進 grep、不把整個 log 讀進記憶體（輸出寫檔、每個套件的 log 有大小上限、結束時只印摘要），也不留下殘留的 Godot 或 grep 程序。這一項和 2026-11-28 一支 grep 吃掉 14.5 GB 記憶體的事故直接相關。
5. 攻擊權杖「同時預兆最多兩個」在高負載下出現過 3 個：查是不是真的競態。
6. run_controller_storage 探針在 Windows 上一定失敗：修成 Windows 與 Linux 都過。
7. bubble_source 探針多支同時跑時偶爾多一行「ObjectDB instance leaked」而判失敗：查是真的洩漏還是結束順序。
8. 章節文件數寫死在測試裡（第一章地圖測試的 5 份、收集品測試的 ch1_kasa 與 chapter_01、chapter_02）：改成讀各章的收集品資料。
9. 換區域途中死亡時跳出「進度尚未保存／重試保存／留在目前區域」：判斷這時候該不該問；可以安全地留在目前區域走正常死亡流程就不要問。

### 來源
2026-11-28，主 session 轉達前一個玩法 session 留下的已知問題、地圖線發現的第四章探針失敗、演出線遇到的死亡存檔提示，以及使用者因記憶體與硬碟被吃滿而定下的測試規則。

# Commit-1

## 內文

每一項的結論：

1. **第四章冷啟動沒回到安全臺**：在目前的 main 重現不出來。照地圖線說的鏈跑（接線廊寫檔 → 工作帶 `--from-safety` → Atropos `--from-work` → 原帳冷啟動繼續，同一個存檔資料夾）四步都通過；Atropos 用原生視窗寫檔、再無頭冷啟動原帳也通過；玩家情境（在 Atropos 競技場存檔、另開程序按繼續）回到清理線安全臺、站在地上、兩個結果旗標都在。已向主 session 要當時失敗的確切指令與 commit 以便 bisect；這條鏈從此有自己的執行器 `tools/run_ch4_save_chain.py`，進了測試挑選與 CI（每次都會檢查「冷啟動回到安全臺」），之後再壞會被抓到。
2. **不在挑選與 CI 裡的探針**：143 支裡有 117 支兩邊都沒有。其中 80 支是要視窗或 GPU 的畫面、量測與單次驗證工具，不適合放進無頭 CI；30 支是各章的流程與存檔鏈探針、7 支是 tests/probes 底下沒有執行器的流程檢查，清單與建議見[探針盤點](attachments/NE-431-probe-inventory.md)。這張先把第四章存檔鏈放進去，挑選規則也認得 `res://tools/chN_*_probe.tscn`，其餘章節之後一章一支補。
3. **挑選工具挑得準**：原本有三個問題——改一支腳本時，停在它自己的資料檔（`grunt.gd` → `grunt.tres` 被當成核心，只挑出 1 個）；改資料時沿著「某支程式寫了這個路徑」一路擴散到程式之間的引用（改一個關卡挑出 58 個）；被牽連到的測試套件又擴散到「借用它共用函式」的其他套件。現在：腳本的資料實例視同一起改了；從資料出發碰到程式只再找測試；關卡之間的出入口不互相牽連；只掃資料夾的大型目錄不算受影響（專門的場景稽核照樣算）。改前改後挑出的套件數：

|---|---|---|---|

| `data/enemies/grunt.tres` | 48 | 62 | 加上經由關卡用到它的測試 |
| `game/enemies/enemy.gd` | 67 | 73 | 共用敵人程式本來就該跑大部分 |

   已知的界線：道具的節點程式（例如輸送帶）只經由關卡核心程式被建立，靜態分析看不出「哪些關卡放了它」，所以只挑到道具自己的測試；完整一輪由 CI 補。挑選工具的單元測試新增四個情境（資料實例、資料不沿程式擴散、套件不互相牽連、關卡出入口），全部 24 個通過。
4. **跑測試的腳本**：新增共用的 `tools/bounded_run.sh`：每個 Godot 程序的輸出只寫檔、log 上限 64 MB（超過就停掉並只留頭尾）、執行上限 1 小時、停掉時連整棵子程序一起停（Windows 的 Godot console 會再開一個 Godot，以前只停到 console 那支）；被中斷時也一起停。`run_tests_parallel.sh`、`run_tests.sh`（不再把整份輸出印出來，只印失敗與結果）、`run_tests_changed.sh` 的探針都改用它；探針共用的 `tools/runtime_probe.py` 也改成停整棵樹、等待時檢查 log 大小、讀 log 時單行有上限。有自己的檢查 `tools/test_bounded_run.py`（log 爆量、超時、孫程序、正常結束代碼），並用真的 Godot 驗證：10 秒上限停掉後沒有任何殘留的 Godot。
5. **攻擊權杖同時預兆超過兩個**：真的競態。令牌的保留時間用真實時間（毫秒），敵人的預兆用遊戲時間；負載高、頓幀或慢動作讓遊戲時間落後時，預兆還沒結束令牌就過期，第三個敵人就跟著預兆。改成令牌用遊戲時間（關卡每個物理影格推進），測試新增「只有真實時間過去、遊戲時間沒走時令牌不會過期」。這也修掉玩家在慢動作時會遇到的同一個問題。
6. **controller_storage 在 Windows 一定失敗**：探針比對「隔離的使用者資料夾」時，一邊是反斜線的 Windows 路徑、一邊是 Godot 回報的正斜線路徑。改成兩邊都正規化（Windows 不分大小寫）後，Windows 本機通過；Linux 的比對不變。
7. **bubble_source 偶爾誤判洩漏**：3 支同時跑、跑兩輪共 6 次都沒有出現。探針的結尾沒有留下未釋放的節點或計時器；判斷是負載高時結束順序造成的一次性訊息。這次的執行器改成停整棵樹之後，被逾時停掉的程序不會再在背景繼續結束、多印訊息；若之後再出現，執行器的 log 會留著完整的那一行可以追。
8. **文件數寫死**：第一章地圖測試改成「第一章目錄裡要在地圖上撿的文件，每一份都擺在某一區、只擺一次」；收集品測試改成「每章的收集進度和目錄一致」。故事線加一份文件不必改測試。
9. **換區域途中死亡跳出存檔提示**：不該問。換區時如果人已經死了，就取消這次換區、不存新區入口，讓目前區域照一般死亡流程處理（和選「留在目前區域」的結果相同，只是不打斷玩家）；有測試，把這段拿掉時測試會失敗。
