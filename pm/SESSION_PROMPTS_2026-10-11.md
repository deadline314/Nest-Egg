## 共用規則

### 1. 成本

- 克制 token。只讀本組的票與需要的文件段落；大檔（`user_guide.md`、NE-222 等長票）用搜尋或分段讀，不整份讀。不把整份 log 或大段程式貼進對話；測試只看摘要與失敗項。
- 能交出去的工作交 Haiku 5.5 subagent（Agent 工具 `model: haiku`），給明確範圍、檔案與驗收方式，只要它回結論。結果有問題就修正指令再交 Haiku；同一件事超過 3 輪仍不行，改用 Sonnet 5.5（`model: sonnet`）。主 Session 負責驗收，不直接相信 subagent 的「通過」。
- 生成與 GPU 驗收留在主 Session；不同 subagent 不同時改同一個檔案。
- 新東西，或試了兩三次都得不到好結果，先查別人的做法與業界實例再動手，不硬幹。寫明來源與實際看到的內容，沒讀到的不寫成已查證。

### 2. 開始前

1. `git fetch origin`，從最新 `origin/main` 建本 Session 專屬的 worktree 與 feature branch（`feature/<組名>`）。已在合適的獨立 worktree 就沿用。不動其他 Session 的 worktree、分支與 stash，不切換別人的 checkout。
2. Git 作者與提交者設成 `Stanley Li <stanley890314@gmail.com>`，只設本專案（`git config user.name/user.email`，不加 `--global`）。
3. 讀 `CLAUDE.md`、`ai-desktop-ticket` skill 與 `.claude/skills/pm-ticket/SKILL.md`。票是 `pm/` 底下的 markdown 檔，不在 AI Desktop 上開；環境沒有 `ai-desktop-ticket` 就照 `pm-ticket` 加下面第 4 節的留言格式。
4. 讀 `pm/user_guide.md` 的「2026-10-11 新增」段落，以及與本組有關的章節；再讀本組每張票的最新描述、Commit 段落與相依，核對目前程式是否已有實作。
5. 雲端 Session 另外先確認：真的是 Nest-Egg repo、`git fetch` 成功、Godot 可執行、實際記憶體與磁碟額度。任何一項不成立就停下回報。

### 3. 每張票的做法

1. 記下本票開始時的 SHA 當固定基準。票改「進行中」。
2. 實作。程式與架構好維護、好擴充（新增內容以資料為主）、穩定、容錯（資源遺失或資料損毀時記錄具體位置並退回安全預設）、效能與記憶體受控（不每影格配置、用物件池、資源用完清理）、該抽象的才抽象，不為抽象而過度重構。依功能需要注意權限與隔離、錯誤捕捉、逾時與取消、併發。需要引導的地方加精簡的提示與 Hover，一句講重點，不加無關提示。不破壞原有功能。
3. 自我檢查上面各項，修正後跑 `tools/run_tests_changed.sh <固定基準SHA>`，受影響範圍全過（腳本或編譯錯誤也算失敗）。不改測試選擇器、不加 known failure、不刪斷言來變綠。完整測試交給 CI，不自己跑全套。
4. 實際驗收並截圖，存到該專案的 `images/`。畫面類驗收要真的看過畫面。
5. 在票上加 Commit 段落，用「問題—改動—驗收」三段白話文，附截圖、簡短測試結果、分支名與遠端 commit 連結；不寫程式細節。只勾真正通過的驗收條件。
6. 提交前核對內容與身分。commit 訊息與署名不得出現 Claude、GPT、模型名稱或任何 `Co-Authored-By`。一張票一個 commit，先 push 到自己的 feature branch。
7. 全部驗收條件通過：`git fetch origin`，rebase 到最新 `origin/main`，重跑受影響測試，`git push origin HEAD:main`（只能快轉，絕不 force 推 main），票改「審查中」。rebase 改寫了已推送的自己的分支時，確認遠端沒被別人更新後才用 `--force-with-lease`，並更新票上失效的 commit 連結。
8. 驗收還沒全過（例如雲端做不了原生畫面、實體手把或試聽）：成果留在 feature branch 並 push，票維持「進行中」，Commit 段落寫清楚「待本機原生驗收」的項目。不假裝完成，不轉審查。
9. 遠端拒絕操作時不重試、不繞過，回報使用者。

### 4. 票

- 本組的票已存在，先核對並補齊，不重複開同樣需求。既有票範圍內的修正留在原票。
- 發現新的獨立問題：先整理設計與相依，一項需求一張票。開新票前 `git fetch origin`，取該專案資料夾最大編號 +1，只含票檔的 commit 立刻 push 到 main，避免撞號。
- 維護性、擴充性等品質要求落實在設計與程式，不逐項寫進票。

### 5. 範圍

- 只改本組負責的範圍。非動到別組的檔案不可時，改到最小、在票上記錄，並在回報中列出。
- 使用者在指令或對話中新提的在意事項，用一兩句整理進 `pm/user_guide.md` 對應段落，隨當張票一起提交。
- 參考作品：Leyla In Veil（地圖光影、爆炸特效、撿東西丟敵人、油桶爆炸、UI）、Project Revenant（每個頭目有獨立機制與攻擊習慣）。先看過實際畫面或官方資料，借原則與手法，不照抄；Nest Egg 保留高低起伏與多方向地圖。

### 6. 收尾

- 全部票做完後做一次整組相互影響檢查；有修正就補測試、截圖、commit、push，更新對應票的證據與連結。
- 只刪本 Session 已併進最新遠端 main 的本機與遠端分支，清掉對應 worktree。未合併的交付分支保留並列出名稱。不刪別人的分支。
- 最後逐票回報：結果、測試、截圖、commit、票況、尚待處理事項。

使用者的話：目前真的做得很好，相信你的能力。發揮想像力，做一個有趣又有特點的遊戲。
