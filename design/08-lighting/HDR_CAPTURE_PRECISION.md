# HDR 截圖：先轉換色彩，再量化

2026-11-11，接續 NE-223 原生任務背景的診斷，產品背景與燈光不變。取樣來源、重新擷取、縮圖層級與取樣平均的對照沒有證明遊戲畫面損毀；但原始模糊輸出正常，壓暗後的 PNG 出現色帶，需檢查擷取編碼。

現有流程先將浮點線性色彩轉成 RGBA8，再轉 sRGB。接近黑色的 0～0.03 線性亮度，先量化只剩約八個碼；正確的 sRGB 8 位元原本能保留約 49 個碼。丟掉的暗部精度無法靠後續色彩轉換恢復。

需求：從同一份 HDR readback 在浮點精度完成線性到 sRGB 轉換，再輸出 8 位元 PNG；透明度、尺寸與未使用 HDR 的原始位元組保持。只修擷取層，不改遊戲後製、背景、燈光、模糊或曝光來配合截圖。

驗證採獨立分段傳遞函數作參照：RGBAH／RGBAF 的 0～0.03 暗色 ramp，各色版誤差不超過一個 sRGB 位元組步階，保留可用的暗部色階；透明度、原 HDR bytes 不變，LDR bytes 一致。先用原轉換本體做 CPU 負控制，再核對正式公開編碼入口。接著同一份真正 PAUSABLE 關卡的原始 HDR 影格分別輸出舊／新編碼，不跨影格推斷。

所有原始 bytes、測試來源及 SHA-256 收進 raw.zip；manifest 核對 zip 內的原始成員，避免 Git 文字換行正規化改變來源收據。原錯誤探針、圖片與日誌保留，不能把擷取修正冒稱遊戲背景渲染修復。

依據：[Godot Image 文件](https://docs.godotengine.org/en/stable/classes/class_image.html#class-image-method-linear-to-srgb)、[固定 4.7.2 來源](https://github.com/godotengine/godot/blob/4.7.2-stable/core/io/image.cpp)。8 位元線性資料的暗部精度不足，公開圖像方法的格式能力須對照實際版本，不只看最新文件。

## 已驗證的交付

同一份測試來源在原流程 12／4、修正後 12／0。RGBAH 與 RGBAF 各從 8 個提升至 49 個暗部色階，最大 sRGB 誤差分別 0.0039086、0.0038998；alpha、尺寸、來源 bytes 與 LDR bytes 回歸通過。原生中間灰／暗色／透明／非 HDR 回歸亦通過。

同一正式當舖、真正 PAUSABLE 關卡，1280×720 為 11／0、1920×1080 為 14／0，均原生 Forward+、HDR 2D。玩家、鏡頭、畫布變換、遊玩與霧時間前後樣本相同。每個世界／暫停／任務影格同時保留一次 readback 的浮點 bytes 與舊新編碼。獨立逐像素驗證覆蓋六張、8,985,600 像素，最大 sRGB 誤差 0.00392131、alpha 誤差 0；新圖色帶消失且保留當舖輪廓。

第一次標示 1920 的工具啟動後被設定還原為 1280，該批完整封存但不接受為 1080p 證據；新增實際尺寸斷言並重跑真正 1920×1080。原生觀察工具過去 ALWAYS 繼承導致世界未暫停的錯誤另保留原紀錄，不以暫停旗標冒稱世界凍結。
