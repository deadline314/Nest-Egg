# 連續性與小瑕疵檢查 skill

目的：「為什麼會直接回到電話亭？」「該播的診間過場沒播」這類小瑕疵都算 Bug。它們多半是**狀態沒對齊**：旗標在錯的時機寫入、特殊流程被一般流程搶先處理、玩家在某個狀態下看不到前因。這份 skill 是檢查清單與設計規則，交付前逐項對照。
完整資料與出處：`design/09-content/SYSTEMS_REFERENCE.md`（業界做法；標【建議】的是我們的起始值）。章節節奏見 skill `chapter-design`，位置與圖層見 `scene-staging`。

## Bug 分級（建議）

| 等級 | 定義 | 例子 |
|---|---|---|
| S1 阻斷 | 崩潰、資料損毀、卡死無法前進 | 死亡後讀檔卡黑畫面 |
| S2 嚴重 | 主線流程錯誤、關鍵過場未播、狀態錯誤 | 診間過場沒播、死亡後沒有解釋就回電話亭 |
| S3 一般 | 次要功能、文字、音效缺漏 | 提示按鍵錯 |
| S4 輕微 | 外觀細節、對齊 | 站位差幾像素 |

S1、S2 必須在合併前修掉。嚴重度（技術影響）與優先級（緊迫度）分開記。

## 檢查清單（每張涉及流程的票逐項勾選）

**敘事連貫**
- [ ] 每個事件都有前因：玩家在哪、為什麼在那、誰帶他來（尤其是場景切換、醒來、傳送）
- [ ] 角色的物品、裝備、外觀、位置在過場前後一致
- [ ] 對話提到的事實與已發生的事實一致（死亡次數、錢、地點）
- [ ] 同一件事不被兩個 NPC 以互相矛盾的方式講述

**旗標與狀態**
- [ ] 每個旗標：誰寫、誰讀、初始值、重置時機都有記錄；沒有只寫不讀、只讀不寫的旗標
- [ ] 旗標在「事件完成」時寫入，不是「事件開始」；過場被中斷或跳過時的行為明確
- [ ] 新遊戲、舊存檔、缺旗標的存檔都能進行（缺值走安全預設並記錄具體位置）

**過場觸發**
- [ ] 前置條件明確，只在全部滿足時觸發；同一過場不重複觸發（除非設計要求）
- [ ] 特殊流程不會被一般流程搶先處理（例如死亡處理器在過場之前就把玩家傳走）
- [ ] 可跳過，跳過後的狀態與播完相同；已看過的過場重玩或讀檔後行為符合設計

**死亡與重試**
- [ ] 世界為什麼允許復活、為什麼回到這裡，兩層都有交代（第一次完整，之後短）
- [ ] 死亡後各類狀態符合規則：保留（劇情旗標、已開寶箱與捷徑、已解鎖能力、死亡次數、復原點）／重置（HP、局部敵人）／結算（扣款）
- [ ] 結算在畫面轉黑之前寫進存檔（避免關遊戲逃避懲罰）
- [ ] 連續死亡（2、3、10 次）演出正確、不累積記憶體或殘留物件；在復原點、過場邊界、場景切換瞬間死亡也正確
- [ ] 一般死亡從歸零到可操作 ≤ 3 秒（目標 2 秒），超過 5 秒要可跳過；劇情死亡不受此限

**讀檔與重玩邊界**
- [ ] 過場中、戰鬥中、對話中、死亡當下存檔再讀；讀檔後鏡頭、位置、面向、物品、HP 一致
- [ ] 在過場中途讀檔從過場開頭重來，不跳到別處

**場景切換**
- [ ] 鏡頭邊界、跟隨目標、縮放、後製（HDR、雨）都重設；角色不卡牆、不浮空、朝向正確（見 `scene-staging`）

**文字與音效**
- [ ] 沒有 key 名稱或空白字串、沒有溢出框；重要動作有音效；缺資源有記錄與安全預設

**提示與教學**
- [ ] 提示的按鍵與實際按鍵一致；會了就不重複；教學與後續規則一致（例如「電話亭是復原點」前後說法一致）

**可達性與卡死**
- [ ] 每個區域有出口、每個必要道具可取得、每扇門有鑰匙來源；任一狀態（死亡、讀檔、跳過）都不會卡死

## 死亡與復活的設計規則

1. **兩層交代**：先有「世界為什麼允許你復活」，再有「為什麼回到這裡」。缺一層玩家都會問。
2. **復活點是有人或有物的地方**（篝火、房子、艙、電話亭），不是空地；它同時承載存檔、商店、升級，所以玩家願意回去。
3. **第一次死亡教規則，之後用短演出**：第一次特殊死亡（劇情死）用完整過場、可跳過；之後的一般死亡 2–3 秒短演出（暗轉、聲音、一句旁白，前幾次句子輪播），再之後縮到約 1 秒；演出由資料表（死亡場景表：場景 id、條件、可否跳過、結束後復原點、要寫的旗標）指定，特殊場景優先於一般處理。（出處：BioShock、Dark Souls、Hades 的做法）
4. **本專案的銜接**：第一次死亡時凜還沒登記復原點，所以不是傳送，是收屍人把遺體運到復原館（診間）做「初次建檔」；診間過場講清楚三件事（為什麼能活、為什麼這次在這、之後回電話亭，每次復原扣信用點、記憶磨損），結尾電話亭亮起「已登記」；之後所有死亡回電話亭，不再提診間。復原點欄位為空（舊檔、旗標遺失）時退回最近可用的復原點或診間並記錄錯誤。
5. 死亡畫面與等待：失敗應該是快速重試；長死亡動畫會讓每次失敗更煩。

## 貨幣與升級的設計規則

- 先決定有幾種錢、死了會怎樣：一般錢（死亡會扣）、永久成長（不掉）、劇情鑰匙（不能買）；每種都花在有名字的地點（老 K 的當舖、工作檯、電話亭），不是冷冰冰的選單。
- 來源（faucet）與消耗（sink）對帳：每章列「該章可得總金額（含隱藏）」與「價目表總和」，必要升級總價約為主線收入的 60–80%，其餘靠探索補（起始值，要試玩調）。
- 第一章：第一次拿錢在打第一個敵人或破第一個箱子（掉 1–3 枚）；在買得起之前就先看到店與價格；前半段花一筆小錢；能力解鎖靠劇情與探索，不靠錢；一個武器改裝槽、兩三個價差明顯的選項；一兩處不在主路上的小額寶箱。
- 死亡扣款設上限（不超過身上現金、不負債），劇情必死不扣款；取回機制與扣款二選一，避免兩套並存。
- 升級要「有感」：買了立刻在 HUD 或角色上看得見，tooltip 顯示「之前 → 之後」，商店旁放標靶或第一個敵人讓玩家馬上試。
- 價格與收入放資料表，用腳本算每章比例放進測試或報表。

## 自動檢查（優先做這些）

1. 旗標引用檢查：掃描資料，建立「誰寫、誰讀」表，報告只寫不讀、只讀不寫、拼字相近的旗標。
2. 過場前置條件：每個過場宣告 requires 與 sets；requires 的旗標至少有一處 sets；sets 發生在「過場結束」。
3. 孤兒資源：沒被任何資料引用的場景、過場、對話、音效列為警告。
4. 不可達內容：從新遊戲初始狀態模擬旗標圖，找出永遠無法滿足的條件。
5. `once` 對話都寫入已看旗標。
6. 死亡矩陣測試：無頭模式枚舉（第一次死亡是否完成、診間過場狀態、電話亭是否登記、死亡位置、讀檔情境）的組合，走一遍「死亡 → 復活」並斷言（位置在復原點、旗標、錢、無腳本錯誤）。
7. 資源遺失容錯：故意移除一個過場或音效，確認記錄具體路徑並退回安全預設。
8. 長時間 soak：反覆死亡 50 次、換場景，觀察記憶體與殘留節點。

## 工作流程

1. 開工前讀對應章節與 `SYSTEMS_REFERENCE.md`；涉及死亡與旗標的先畫狀態矩陣（欄位 × 預期）。
2. 先寫會失敗的回歸測試（把這次的瑕疵寫成測試），再修。
3. 交付前逐項過上面的清單，在票上勾選並註記不適用的項目。
4. 發現新的瑕疵類型，補進這份 skill（清單、矩陣、自動檢查）。

## 使用者在意的事（2026-10-07；總表見 skill `user-priorities`）

- 文字可讀性是檢查項目：StoryLint 要擋「單獨成句的一兩個字」「連續短子句」「名詞並列斷句」（門檻見 `design/13-story-v2/DIALOGUE_READABILITY.md`，ST-15 實作）；每個場景要能回答「誰在哪裡、要做什麼、為什麼」。
- 流程檢查要涵蓋「每一刻都有進行中的主線目標」（NE-223 的旗標模擬）與「新遊戲到第一章第一個場景沒有死結」（序章，ST-16）。


## 玩家文字交付基線（ST-15；2026-10-07 UTC）

- 先讀 `design/13-story-v2/DIALOGUE_READABILITY.md`；完整句子規則優先於舊「短句」稿。先讓玩家看懂誰在哪裡、要做什麼、為什麼，再處理節奏。
- 對白、旁白、廣播、氣泡、戰鬥短句、NPC、死亡復原、路牌、提示、任務、文件、道具描述與 tooltip 全部納入。角色靠用詞、口氣與關心的事區分；不能靠一兩字獨立斷句或省掉對象表現冷淡。
- 一行最多一個三字以內子句且不相鄰；首次出現的專名在同場景交代身分／地點／用途。名稱、按鈕、編號、數值是標籤，只有明確分類的標籤免用句子門檻；廣播、公文與 formal 講者沒有可讀性豁免。
- 氣泡 ≤ 30 字、戰鬥 bark ≤ 16 字，均須完整；同屏 ≤ 2、不鎖操作；停留 `1.2 + 0.1 × 字數` 秒，上限 4.2 秒。長文依意思分句，不靠截斷或縮成名詞串過關。
- 改 `tools/story/build_ch1_story.py` 的台詞來源後重新生成 `data/story/ch1_kasa.json`；地圖提示同改 `tools/level/build_ch1.py` 與對應 `.tres`。核對產生前後：演員、姿勢、舞台、步驟、旗標、引用不因文字改寫而改動。
- 執行 `godot --headless res://tools/story_lint.tscn -- --out=<報告路徑>`，報告含 live 文字來源與位置；所有錯誤、警告皆須修完。跑受影響的故事／顯示／連續性／節奏測試，再看實際畫面是否溢出、截字、讀不完。
- 逐場景留下「誰／哪裡／要做什麼／為什麼」通讀表與各主要角色五行前後對照；檢查金額、死亡次數、已持有物品及伏筆，不能把建議稿當已實作。
- 文字變長要重算過場秒數與氣泡停留。資料估計、自動播放截圖、人工操作、母語審稿分開記錄，不能代稱遊測。
- 未生成的 NE-223 任務文字／ST-16 序章不得算已檢查；交付合入後重新生成來源並重跑全文掃描與通讀，列明新增覆蓋。設計與實際資料不一致時列出差異及接手條件。

- NE-223 介面合入後，玩家地圖提示含 `core/navigation/quest_map_index.gd`；正式 `quests` 的 background／reward／blocked_reason／suggestion 與任務、步驟 title 必須是完整意思，不能把動作目標當名稱標籤豁免。fixtures 只驗 UI；來源尚未生成就留待補驗。

- 既有日英文 `ja`／`en` 與章節副標題 `sub` 亦納入來源盤點；翻譯對照語義與母語審稿分別記錄，不能以中文的零警告代稱母語驗收。


## 2026-10-20：保存被拒絕的完成邊界（NE-246）

- 最後一句確認不代表保存成功；重要通訊在耐久提交前不發布完成旗標／已讀通知，也不讓背景自動保存繞過待處理結果。
- 拒絕、重試、取消、死亡、正常退出與新程序續玩分開驗。比對「提交前同一刻」的原檔 bytes，閱讀途中合法的舊狀態自動保存不能拿來冒充拒絕後覆寫。
- 重試重新準備當下候選；取消保留未讀、釋放自己擁有的鎖。已提交後若來源改變，保留提交事實，走正式續玩還原，不能提供放棄已保存結果。
- 觀察者收到完成旗標時，磁碟與全部被安裝的狀態必須已一致。旗標完成不重建世界、敵人、活子彈或導覽容器。
- 探針的觀察 Node 可 PROCESS_MODE_ALWAYS；真正 Main／Level 仍維持正常可暫停的繼承。原生證據標示安排位置、合成輸入與軟體渲染，不當成真人通關。

- 回滾也失敗時，未提交結果與已提交結果的恢復文案分開；前者可從 Main 讀完整原備份，不得誤說本次結果已保存。旗標型安裝不得順手保存卻不安裝道具／錢包修復。
